# Dartmouth Energy Twin

> Visualizing the invisible infrastructure powering Dartmouth College.

Dartmouth Energy Twin is an interactive 3D digital twin for exploring Dartmouth College's campus, buildings, and future energy systems. The project is evolving from a place-discovery map into a campus infrastructure visualization tool focused on sustainability, building intelligence, and immersive spatial context.

## Vision

Most campus maps show where buildings are. Dartmouth Energy Twin aims to show how the campus works.

The long-term product will combine a realistic 3D campus, clickable smart buildings, underground energy infrastructure, animated energy flows, and dashboards that explain how Dartmouth's built environment uses and transforms energy.

## Current MVP

The current app is a standalone, Dartmouth-only 3D scene (Three.js) — no globe, no streamed terrain:

- Campus rectangle as the whole world: pre-built bare-earth terrain, aerial imagery, roads, paths, fields, trees and buildings
- All 719 OSM buildings from the assembled campus model, with measured heights and reference-based colors
- Clickable buildings (the 3D geometry itself) and entrance markers
- Orbit, pan, zoom, reset, building fly-to, ground view, and an overhead minimap
- Public-record energy evidence: badges and technology-tinted buildings that never alter base colors
- Energy-network, carbon and future-work layers; seasonal trees and day/night lighting
- Quality settings (auto/low/medium/high) and on-demand rendering
- Building profile side panel
- Street View entrance preview when a Google Maps key is configured
- Bundled Dartmouth building data with Supabase fallback support
- Search and category filtering
- Time-of-day and seasonal atmosphere controls
- Responsive interface

## Environment Variables

The 3D map needs no keys. Copy `.env.example` to `.env.local` and fill in only what you want:

```env
# Optional: Street View photos in the building panel (server-side only, never sent to the browser)
GOOGLE_MAPPLATFORM_APIKEY=
# Optional: read buildings from Supabase instead of the bundled data
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_ANON_KEY=
```

- `GOOGLE_MAPPLATFORM_APIKEY` (or `GOOGLE_MAPS_API_KEY`) is read only by `/api/streetview`. Without it the panel shows its illustrated placeholder. Restrict the key to the Street View Static API.
- `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` are public by design (anon key + row-level security). Without them `/api/buildings` serves the bundled buildings.
- `NEXT_PUBLIC_CESIUM_ION_TOKEN` is no longer used and can be deleted.
- Never prefix a secret with `NEXT_PUBLIC_`; those values are compiled into the client bundle.

## Scene Assets

Everything the map draws is generated ahead of time and committed under `public/models/dartmouth-campus/`; normal requests never run Blender, Python, scrapers, or live terrain sampling.

| Asset | Generated by | Source |
|---|---|---|
| `dartmouth-campus-styled.glb` | `npm run model:dartmouth:combine`, then `python3 scripts/blender/style-campus-glb.py` | Blender export + NH GRANIT heights + reviewed color references |
| `terrain/campus-terrain.{bin,json}`, `terrain/campus-imagery*.jpg`, `terrain/building-ground.json` | `python3 scripts/terrain/build-campus-terrain.py` (needs `rasterio numpy pillow scipy`) | USGS 3DEP DEM, USGS National Map orthoimagery |
| `campus-roads.json` | `node scripts/reference-tools/fetch-dartmouth-osm-roads.mjs` | OpenStreetMap |
| `campus-fields.json` | `node scripts/reference-tools/fetch-dartmouth-osm-fields.mjs` | OpenStreetMap |
| `campus-trees.json` | `python3 scripts/reference-tools/fetch-campus-trees.py` (needs `rasterio numpy scipy`) | Meta & WRI canopy height |

Re-run the terrain script whenever the styled GLB changes (it records each building's ground elevation). `campus-terrain.json` lists the attribution, content hashes (used as cache-busting `?v=` parameters) and known approximations: ground is bare earth on a ~2 m grid, buildings sit on the lowest ground under their footprint, and the imagery is a 2024 capture.

Performance against the former Cesium view is documented in `docs/perf/renderer-comparison.md`.

The modeling reference atlas is available at:

```text
http://localhost:3000/reference-atlas
```

It gives modelers front, side, and back Street View reference slots for each tracked campus building.

To generate local orientation images for every tracked building, run:

```bash
npm run reference:images
```

The images are written to `public/reference-atlas/images/` and are ignored by Git so the repository does not balloon. The atlas uses these local images first, then falls back to live Street View when a local image is missing.

For actual modeling references across every OSM building inside the Dartmouth rectangle, generate facade candidates instead:

```bash
npm run reference:open:dartmouth-hall
npm run reference:open:test
npm run reference:open
npm run reference:wikimedia:dartmouth-hall
npm run reference:wikimedia:test
npm run reference:wikimedia
npm run reference:facades:plan:test
npm run reference:facades:plan
npm run reference:facades:guides
npm run reference:facades:test
npm run reference:facades:multi
npm run reference:facades
```

Use the open-source generator as a lead finder, not as the final Maya reference set. It searches named OSM buildings against free/open image providers such as Wikimedia Commons, Openverse-indexed media, and the Library of Congress, then rejects obvious non-modeling images such as maps, aerials, interiors, logos, low-resolution files, narrow crops, construction scenes, and metadata-obstructed photos. Saved candidates include provider, source link, license metadata, checker notes, and manual-review flags. Because web images are often mislabeled, do not trust them as front/back/side views until manually approved.

The Wikimedia-only generator is still available when you want a narrower source pass. It is useful for quick debugging because the results are usually easy to inspect and attribute.

The Street View facade generator is the preferred four-view modeling pass. It pulls building footprints from OpenStreetMap, selects the major walls from the map geometry, records each face length and bearing, then samples multiple ground camera candidates on both sides of each face. It scores candidates by straight-on angle, useful distance, and full-face field of view before saving wall-facing images as `front.jpg`, `back.jpg`, `left.jpg`, and `right.jpg` where possible. The goal for each candidate is one complete building face from corner to corner. Use `reference:facades:plan:test` first so you can inspect camera choices before downloading images; use `reference:facades:multi` only when you intentionally want two options per face.

The checker is intentionally conservative: it discards photos whose metadata suggests blocked walls, trees, branches, leaves, vegetation, vehicles, crowds, scaffolding, snow, night/low-light views, partial crops, or close-up details. Final approval still requires a human or a vision API to confirm that the actual pixels show the wall end-to-end without foreground obstruction.

For small obstructions, use source-preserving cleanup only. Keep the original photo as the ground truth, mask only the tree/vehicle/foreground object, and repair that masked region from the surrounding real facade or overlapping approved views. Do not generate a whole new facade, change the roofline, invent window spacing, replace doors, or synthesize a full wall from scratch. If the obstruction covers a large or structurally important part of the face, mark the shot as a cleanup candidate and use another view, field capture, or map-derived guide instead.

If every photo for a face has trees, generate map-derived guide sheets instead:

```bash
npm run reference:facades:plan:test
npm run reference:facades:guides
```

The guide sheets are written to `public/reference-atlas/guides/` and ignored by Git. They are tree-free dimension guides from the flat map: wall length, bearing, endpoints, and candidate camera positions. They are not photo references and should not be used to invent exact windows, doors, materials, trim, or roof details. Use them to model correct massing and to constrain any later AI cleanup/inpainting from approved photos.

If an OSM building name is wrong or incomplete, add the correction in:

```text
scripts/reference-tools/campus-building-names.mjs
```

The open-source, Wikimedia, and Street View facade generators all use this shared naming helper before writing atlas manifests.

When the free images are useful but each one has small blocked areas, open:

```text
http://localhost:3000/reference-compositor
```

The compositor reads the same generated manifest, stacks multiple candidate images for a building, and lets a modeler adjust visibility, opacity, scale, rotation, position, and blend mode. Export the result as a PNG reference sheet after aligning the clearest visible wall parts. This is a free/manual path for combining partial references before spending money on vision review or new image capture.

Use the atlas review controls before compositing. Normal modeling mode shows strict v2 approved references only. Mark only images that show the full building face from corner to corner with no trees as approved. Reject any image with trees, partial walls, wrong buildings, or bad angles; unapproved and rejected references are excluded from the compositor. Old approvals from earlier image-search passes are ignored so tree-obstructed photos cannot survive a browser refresh.

## Supabase Setup

Run this migration in the Supabase SQL editor:

```text
supabase/migrations/202607010001_mapwrld_core.sql
```

Then add the Supabase project URL and anon key to `.env.local`. The app reads building data through `/api/buildings`, caches responses for five minutes, and automatically falls back to bundled data if Supabase is unavailable.

## Model Import Workflow

The app is prepared for a future custom Dartmouth campus model at:

```text
public/models/dartmouth-campus/dartmouth-campus.glb
```

Use this workflow when exporting from Maya:

- Model and export in meters.
- Keep the campus centered around the manifest origin in `public/models/dartmouth-campus/model-manifest.json`.
- Export as binary glTF (`.glb`) for web delivery.
- Keep geometry modular enough to optimize or replace buildings later.
- Reduce unnecessary bevels, hidden faces, duplicate objects, and high-density trees before export.
- Use baked/simple materials first; add detailed materials only after performance is acceptable.
- Place the exported file at `public/models/dartmouth-campus/dartmouth-campus.glb`.
- Change `status` in `model-manifest.json` from `pending` to `ready` after the file is in place.

The map loads whatever `campusModel` points to (the styled GLB). After replacing it, re-run the terrain script so building ground elevations match.

For the full GeoJSON -> Blender -> Maya -> GLB pipeline, use:

```text
public/models/dartmouth-campus/README.md
```

## Deployment (Vercel)

Production: https://dartmouth-energy-twin.vercel.app (Vercel project `dartmouth-energy-twin`, connected to this GitHub repository; `vercel.json` pins the Next.js framework preset).

1. Generate and commit scene assets (see Scene Assets). Vercel only runs `next build`.
2. `npm run check:assets` (exact-case paths, nothing needed is in `.vercelignore`), then `npm run build && npm start`, and check http://localhost:3000, `/api/buildings`, and a building's Street View photo.
3. Push a branch: every push to a branch other than `main` creates a Preview deployment (shown in the Vercel dashboard and on GitHub). Previews are behind Vercel Authentication; sign in, or use `vercel curl <preview-url>/api/buildings` for quick checks. Verify the map, assets, `/api/buildings`, `/api/streetview`, navigation and the mobile layout.
4. Promote the verified preview: `vercel promote <preview-url>` (or "Promote to Production" in the dashboard). Merging to `main` also deploys production.
5. Optional environment variables live in the Vercel project (Settings → Environment Variables). `GOOGLE_MAPPLATFORM_APIKEY` is set as a sensitive variable for Preview and Production; add the Supabase pair there if you use it, then redeploy.

Deploy through Git rather than `vercel deploy` from a laptop: the deployment has about 6,900 files (mostly the per-building renders used by `/design-space`), and the Hobby plan caps CLI uploads at 5,000 files per day.

Deployment details:

- `.vercelignore` keeps secrets, Blender sources, offline pipelines, raw rasters, and model intermediates out of the deployment; the per-building renders used by `/design-space` stay. `/reference-atlas` images are generated locally and gitignored, so Git deployments show that page's empty state.
- `next.config.ts` traces `osm-campus-names.json` into the `/api/buildings` function, marks hashed terrain/imagery files as immutable, and gives other scene data a one-hour cache with background revalidation.
- Static assets are served from Vercel's CDN. The scene downloads about 4 MB; object storage is not needed at this size.

Rollback: in the Vercel dashboard, open Deployments and "Promote to Production" (instant rollback) on an earlier deployment, or `vercel rollback`. In Git, the last Cesium version is commit `52622c4` (Cesium at `/`, the standalone scene at `/preview`); `git revert` the migration commits on a branch to restore it, and re-add `NEXT_PUBLIC_CESIUM_ION_TOKEN`.

## Known Limitations

The map is a planning and storytelling tool, not a survey. Known approximations and gaps:

### Terrain and imagery
- Ground is the USGS 3DEP bare-earth DEM resampled to a ~2 m grid; small features (curbs, steps, retaining walls) are smoothed out.
- The aerial imagery is the USGS National Map's 2024 autumn capture at ~0.38 m per pixel, so it blurs at street level and shows roofs and tree crowns that the 3D layers also draw.
- Seasons are approximate: winter is a light snow wash over the autumn imagery, and the other seasons only recolor trees.
- Day and night use a simple sun arc for lighting; there are no shadows, street lights, or weather.

### Buildings
- Buildings are rigid and sit on the lowest ground under their footprint, so on slopes the uphill side is partly embedded (up to ~10 m on the river slope).
- Heights come from a January 2020 NH GRANIT nDSM (median of interior lidar pixels) or OSM tags; many are flagged for review in `building-heights.json`.
- Most buildings are footprint massing with reference-based colors; only Baker Library and Dartmouth Hall have detailed models.
- Buildings whose OSM center falls outside the campus rectangle are left out.
- Supabase-only buildings without OSM ids can be selected from markers and search but not by clicking their 3D geometry.

### Layers and data
- Roads, paths and fields come from OpenStreetMap and are only as complete as OSM; baseball diamonds and beach volleyball courts have no line markings, and running tracks show their edges but not individual lanes.
- Trees are detected treetops from Meta & WRI's canopy-height map; positions are approximate and the broadleaf/conifer split is random, not real species.
- The district-heat and electric networks are schematic links between hubs, not surveyed pipe or cable routes.
- Building energy figures (demand, annual use, emissions, scores) on hand-authored buildings are planning estimates; generated buildings show "TBD" until real metering is connected.
- Public-record energy evidence comes from keyword and name matching of public Dartmouth pages and is unreviewed.

### Interface and rendering
- Markers draw on top of buildings rather than being hidden behind them.
- The whole terrain and every tree are drawn in every frame (no level-of-detail), about 0.56 M triangles at medium quality; low quality reduces the terrain mesh for phones.
- Changing the quality setting reloads the scene.
- There is no keyboard or first-person navigation yet; ground view is a low orbit.

### Deployment
- `/reference-atlas` and `/reference-compositor` use locally generated, gitignored images, so Git-based Vercel deployments show their empty state.
- Preview deployments sit behind Vercel Authentication.
- The Hobby plan allows 5,000 CLI file uploads per day, so deploy through Git rather than `vercel deploy`.
- Performance figures in `docs/perf/` come from one Apple M2 machine in a headless browser; other hardware will differ.
